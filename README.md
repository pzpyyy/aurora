# Aurora

#### 介绍
多功能清理模块
本模块追求极低开销实现清理
方案一：传统 Cron 方案
核心工作机制
Cron 是一个经典的任务调度器，它采用固定频率轮询的设计思路。每60秒准时唤醒一次，严格检查任务表中是否有需要执行的任务。

功耗表现分析
在测试场景中（10个集中在凌晨1-2点的任务），Cron 展现出了明显的能效问题：

24小时唤醒模式：

从00:00到00:59：执行60次无效唤醒（无任务）

从01:00到01:59：60次唤醒中执行10个实际任务

从02:00到23:59：执行1320次无效唤醒

能效缺陷：
为了1小时的有效任务执行，系统付出了23小时的无效唤醒代价。这种"宁可错杀一千，不可放过一个"的设计哲学，在移动设备上造成了显著的能源浪费。

适用场景
Cron 更适合服务器环境，其中稳定的电源供应和固定的工作负载使得每分钟唤醒的开销可以接受。但在电池供电的移动设备上，这种设计显得过于奢侈。

方案二：While + Sleep 轮询方案
核心工作机制
这是最简单的定时实现方式：通过无限循环配合睡眠间隔来实现任务检查。每秒唤醒一次，检查是否有任务需要执行。

功耗表现分析
24小时工作模式：

总共执行86,400次唤醒（24小时 × 3600秒）

其中仅10次是有效任务执行

无效唤醒比例高达99.99%

能效灾难：
这种方案的功耗表现是最差的。每秒固定的唤醒节奏完全无视实际任务需求，造成了巨大的能源浪费。在移动设备上，这种方案可能导致电池续航缩短5-10%。

技术缺陷
除了功耗问题，sleep函数的精度问题也会导致任务执行时间漂移，长期运行后可能出现明显的定时误差。

方案三：本方案（单TimerFD + Epoll）
核心工作机制
本方案采用事件驱动的智能调度策略，彻底改变了前两种方案的轮询模式：

关键技术：

使用Linux内核的timerfd创建精确定时器

通过epoll实现事件阻塞等待

动态计算下一个最近任务的执行时间

功耗表现分析
智能唤醒模式：

00:00至00:59：完全休眠，零唤醒

01:00至01:59：按10个任务的具体时间精确唤醒10次

02:00至23:59：完全休眠，零唤醒

能效优势：
24小时内仅唤醒10次，且每次唤醒都有明确的任务执行目标。无效唤醒率为0%，实现了"按需工作"的理想状态。

移动设备优化特性
深度睡眠支持：
在无任务时段，系统可以进入深度低功耗状态，不会因为定时任务而阻止CPU降频、核心关闭等电源管理功能。

精准事件触发：
通过内核级定时器，唤醒时机精确到秒级，避免了用户态轮询的精度损失和额外开销。

资源友好设计：
单定时器架构减少了系统调用次数，批量任务处理优化了CPU使用效率，为移动设备提供了最佳的功耗表现。

实际用户体验
续航影响：几乎无法感知的电池消耗

系统流畅度：不会因后台任务导致界面卡顿

发热控制：减少不必要的CPU活跃时间
